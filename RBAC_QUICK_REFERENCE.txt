APPROVAL WORKFLOWS:
┌─────────────────────────────────────────────────────────────────────────┐

│                                                                          │
│  Step 2: Notify Bendahara                                              │

┌─────────────────────────────────────────────────────────────────────────┐

│   ├─ Can see: Only Mosque 1 data                                       │
│   ├─ Cannot access: Mosque 2 data                                      │
│   └─ System blocks: Unauthorized tenant access                         │

API ENDPOINT PATTERN:
┌─────────────────────────────────────────────────────────────────────────┐
│ All endpoints should follow this pattern:                               │
│                                                                          │
│ POST /api/donasi/approve                                                │
│   Headers: X-Tenant-Id: mosque_123                                     │
│   Body: { donasiId, notes, ... }                                       │
│                                                                          │
│ Middleware verifies:                                                    │
│   1. User authenticated (JWT token)                                     │
│   2. User has access to tenant                                          │
│   3. User has 'donasi:approve' permission                              │
│                                                                          │
│ Service then:                                                           │
│   1. Verify Bendahara role specifically                                 │
│   2. Update approval workflow                                           │
│   3. Update donasi status                                               │
│   4. Update Kas balance                                                 │
│   5. Create audit log                                                   │
│   6. Send notification                                                  │
└─────────────────────────────────────────────────────────────────────────┘

FLOW EXAMPLES:

Example 1: Jamaah Creates Donation
  1. Jamaah calls: POST /api/donasi { amount: 500000, ... }
  2. Middleware: Verify tenant access
  3. Service: Check 'donasi:create' permission ✓
  4. Create donasi with status PENDING_APPROVAL
  5. Create approval workflow for Bendahara
  6. Log to audit trail
  7. Send email to Bendahara
  8. Return: Donasi created, waiting approval

Example 2: Bendahara Approves
  1. Bendahara calls: POST /api/donasi/123/approve { notes: '...' }
  2. Middleware: Verify tenant access
  3. Service: Check 'donasi:approve' permission ✓
  4. Verify Bendahara role specifically
  5. Update donasi status to APPROVED
  6. Update Kas balance (increase)
  7. Create audit log with before/after values
  8. Send notification to Jamaah
  9. Return: Approved, Kas updated

Example 3: Compliance Report Generated
  1. System (midnight 1st of month)
  2. Query all transactions for previous month
  3. Calculate statistics
  4. Generate HTML report
  5. Email to stakeholders
  6. Store in database
  7. Can be exported later

SECURITY CHECKLIST:
  ✓ Tenant isolation at every query level
  ✓ Permission verified at middleware + service
  ✓ Audit trail captures all changes
  ✓ Role-based access control enforced
  ✓ Sensitive data not logged
  ✓ IP address & user agent tracked
  ✓ Rate limiting on sensitive endpoints
  ✓ HTTPS required for API
  ✓ JWT tokens with expiry
  ✓ Regular backup of audit logs
